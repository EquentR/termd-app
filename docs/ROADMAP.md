# 里程碑路线图

> 草案。以「可演示的结果」为完成标准。移动端（尤其 Android）团队经验不足，其技术栈在 M0 中先行调研再定。

## M0 — 奠基与关键选型
- **首要任务：选定 daemon 端的终端组件/VT 库**（PTY 管理 + 虚拟终端状态机 + 渲染输出），写 ADR。这是解决渲染与状态问题的核心。
- 确定 daemon/relay 语言、移动端框架（Compose / Flutter / 其他）并写 ADR。
- 协议 v0 草案：握手与密钥、输入事件（键/鼠标）、resize、屏幕状态/增量更新、会话管理、版本协商。
- 威胁模型：relay 不可信；daemon 生成密钥、客户端配对方式。
- 目录骨架、CI、lint。
- **完成标准**：ADR 与协议草案评审通过，CI 绿。

## 第一阶段目标（M1–M3，对应首周三条主线，可并行；实际耗时预计超过一周）

### M1 — Daemon：PTY 管理与渲染
- 同时持有并管理多个 PTY（创建/列出/销毁/resize）。
- Daemon 端虚拟终端维护屏幕状态，并能导出当前渲染结果与增量。
- 本地 CLI 验证：断开再连，直接看到当前屏幕。
- **完成标准**：多 PTY 常驻，重连后屏幕状态正确（vim/htop 等全屏程序可用）。

### M2 — Relay 与 E2E 协议（初版，可扩展）
- Daemon 生成密钥；客户端凭密钥经 Relay 连接。
- 端到端加密通道；Relay 只转发密文。
- Daemon 出站连接 Relay，自动重连。
- **完成标准**：daemon 在 NAT 后，远端测试客户端经 Relay 完整使用终端，Relay 侧抓不到明文。

### M3 — App：基础字符渲染
- 渲染 daemon 下发的屏幕状态；发送键盘/鼠标输入与 resize。
- 先跑通基础终端，细节后置。
- **完成标准**：真机连接 daemon 并操作 shell。

## M4 — 打磨（耗时最长）
- 软键盘与快捷键栏、手势、颜色/字体/宽字符与 IME、滚动与 scrollback 策略。
- 切后台/网络切换后的重连体验。
- 增量更新的带宽优化。

## M5 — 安全加固与多会话
- 密钥轮换/设备撤销、重放防护、限速、审计日志（不含内容）。
- 多会话/多主机管理。

## M6 — 发布准备
- Relay 自托管文档与 Docker 镜像；Daemon 的 systemd/launchd 打包。
- 协议版本兼容策略；文档与发布。

## 待决问题

- 屏幕状态下发形式：整屏快照 + 行级增量，还是渲染后的字节流？
- 移动端技术栈；Android 是否第一期支持。
- 密钥配对与分发方式（二维码/一次性码）；加密方案（Noise 等）。
- scrollback 由 daemon 持有并按需分页下发？
